# ZCU104 HIL bring-up: the PS-PL isolation wall

VERIFIED 25 Aug 2026. This is the root cause of `[Labtools 27-3361] The debug hub
core was not detected` on this board, and the fix.

## Symptom

Vivado Hardware Manager reports:

    [Labtools 27-1434] Device xczu7 ... has no supported soft debug core(s) in it
    [Labtools 27-3361] The debug hub core was not detected
    [Labtools 27-3413] Dropping logic core 'kv_guard_bd_i/ila_lifecycle' ...

while `xsct` DOES show a `Legacy Debug Hub` node under the PL tap, the device
programs cleanly (`End of startup status: HIGH`), and `get_debug_cores` on the
implemented design returns both `dbg_hub` and the ILA.

## Root cause

`pl_clk0` is the ONLY clock net in the block design. It is generated by the PS and
must cross the PS-PL boundary through voltage level shifters whose enables are
gated by the PL power domain (UG1085 p.34). That wall is dropped by a PMU service
request, not by clock configuration.

`psu_ps_pl_isolation_removal_data()` exists in the XSA's own `psu_init.c` but
**`psu_init()` never calls it**. Its only callers are inside FSBL, and every guard
fails in a JTAG-side-loaded flow:

| caller | guard | why it fails here |
|---|---|---|
| `xfsbl_partition_load.c:1649` | destination device is PL | no PL partition in a boot image |
| `xfsbl_handoff.c:752` | `ResetReason == PS_ONLY_RESET` | not a PS-only reset |
| `xfsbl_handoff.c:791` | boot mode is JTAG **and** `PL_DONE` | `BOOT_MODE_USER = 0xE` (SD1) |

So `CRL_APB` gates `pl_clk0` on (`CLKACT=1`) while no edges reach the fabric. A
debug hub with no clock cannot answer, which is precisely 27-3361 resolution note 1.

This also explains why `C_ENABLE_CLK_DIVIDER` and every `BSCAN_SWITCH_USER_MASK`
value made no difference: all are irrelevant when the hub has no clock.

## Fix

Bit 23 = PL in all three PMU_GLOBAL registers.

    mwr 0xFFD80118 0x00800000     ;# REQ_PWRUP_INT_EN.PL
    mwr 0xFFD80120 0x00800000     ;# REQ_PWRUP_TRIG.PL
    mrd 0xFFD80110                ;# REQ_PWRUP_STATUS, bit23 must read 0

MEASURED effect on `CSU_PCAP_STATUS` (0xFFCA3010):

    before  0x80000FD2    PL_INIT=0  PL_DONE=0  pcfg_gwe=0  pl_cfg_used=0
    after   0xA0002FDE    PL_INIT=1  PL_DONE=1  pcfg_gwe=1  pl_cfg_used=1

Then `refresh_hw_device` in Vivado returns `hw_ila_1`, depth 2048.

## Correct PCAP_STATUS bit map

From `zynqmp_pmufw/src/csu.h` and `zynqmp_fsbl/src/xfsbl_hw.h`:

    b0 wr_idle   b1 rd_idle   b2 PL_INIT   b3 PL_DONE   b4 PL_EOS
    b5 pl_seu_error   b6 pl_cfg_reset_b   b7 pl_fst_cfg
    b13 pcfg_gwe   b30 pcfg_pl_cfg_used   b31 pcfg_fuse_pl_dis

`PL_EOS` (b4) is what Vivado prints as "End of startup status: HIGH".

## Two registers that mislead

- `REQ_ISO_STATUS` (0xFFD80310) reading 0 does **not** mean isolation is removed.
  Its reset value is 0 and isolation removal does not go through it.
- `0xFFCA0034` is `CSU_JTAG_CHAIN_STATUS`, **read-only**. Value `0x3` means the PL
  TAP and ARM DAP are both in the chain. It is not a DAP config register.

## Working order

1. `hw_server` started once and kept alive for both xsct and Vivado.
2. xsct: download and run `fsbl_a53.elf` on Cortex-A53 #0 (brings up the PLLs).
3. xsct: the isolation-removal sequence above.
4. Vivado: `connect_hw_server -url TCP:127.0.0.1:3121`, then program the PL
   **from inside the Vivado session** (its chain scan clears a PL configured
   earlier from xsct), then `refresh_hw_device -update_hw_probes true`.
